MoniteurConnect

La plateforme qui relie les auto-écoles et les moniteurs indépendants —
de l'annonce au contrat signé électroniquement.

Le problème

  • Les auto-écoles peinent à recruter des moniteurs diplômés ;
  • les canaux généralistes ne vérifient ni le diplôme, ni l'autorisation d'enseigner, et imposent un compte aux candidats ;
  • le dossier de recrutement (CV, identité, permis, autorisation) puis le contrat restent un processus manuel et dispersé.
Poser le décor en 40 secondes. Insister sur la double friction : côté école (dossiers incomplets) et côté moniteur (un compte par plateforme).
0–3 min · le besoin

Trois acteurs, trois besoins

L'auto-école

Publie, reçoit des dossiers complets, contractualise. Seul compte en libre-service.

Le moniteur indépendant

Cherche, postule avec ses pièces, suit son dossier et contresigne — sans créer de compte.

L'administrateur

Modère, suspend, purge — espace séparé, compte créé par script.

« Sans compte moniteur » est LE choix produit central — il reviendra dans la démo et sûrement dans les questions.
0–3 min · le besoin

La solution : un job board métier

Annonces qualifiées, candidature en une page avec 4 pièces vérifiées, workflow d'acceptation jusqu'au contrat PDF signé par les deux parties. Pas une marketplace : pas de paiement, pas de planning.

Architecture

navigateur → routes → middlewares (session · CSRF · auth) → contrôleurs → services (Prisma, PDF, emails, géo) → vues Twig

  • Une responsabilité par couche, un module par domaine ;
  • toute requête de gestion scopée par schoolId (isolation entre écoles) ;
  • services externes (Sirene, Adresse, Nominatim) relayés en interne et jamais bloquants.
Rendu serveur assumé : chaque page est indexable, le JS n'existe que là où il apporte (carte, pad, graphiques, autocomplétion).
6–10 min · technique

Technologies et pourquoi

  • Express 5 + Twig : rendu serveur, autoescape, SEO naturel ;
  • Prisma : schéma versionné, migrations, requêtes paramétrées ;
  • SQLite → PostgreSQL : code Prisma portable, migrations PostgreSQL dédiées et répétées avant production ;
  • sessions en base plutôt que JWT : révocables, HTTP-only ;
  • Leaflet auto-hébergé, PDFKit, Nodemailer — aucune ressource externe dans les pages (CSP stricte).
Chaque choix a son alternative rejetée et sa raison — détails prêts pour les questions (questions-reponses.md).
6–10 min · technique

Environnements

  • Configuration par variables d'environnement (.env.example versionné) ;
  • fail-fast : refus de démarrer sans SESSION_SECRET ;
  • développement : SQLite, emails en console ou Mailpit local ;
  • production (préparée) : PostgreSQL, cookies secure, trust proxy, SMTP authentifié ;
  • tests : ports dédiés (4055-4070), services externes court-circuités par variables (GEOCODING_DISABLED…).
Le même code sert les trois environnements — seules les variables changent. C'est vérifiable dans src/app.js.

L'intégrité vient de la base

  • School.siret unique — la collision en course devient un message utilisateur (erreur Prisma P2002 gérée) ;
  • Contract.applicationId unique — le 1-1 est garanti par la base : impossible de générer deux contrats pour une candidature ;
  • cascades onDelete — pas d'orphelins, et le code supprime les fichiers privés avant la ligne ;
  • 13 migrations versionnées rejouables : npx prisma migrate deploy.
Le point qui compte : ces contraintes sont testées (correctifs, lot G, smoke). La base n'est pas qu'un rangement, c'est une ligne de défense.

Focus code : la signature électronique

signature école (pad/import) → validation de l'image → PDF proposé + SHA-256 + horodatage → invitation email → contre-signature par jeton → PDF final (2 signatures, nouvelle empreinte) → invalidation si ré-édition

  • Front, back, base, fichiers privés, crypto et emails dans un seul flux ;
  • 49 assertions écrites avant le code (test/lot-g.cjs).
Annoncer le plan des 3 diapos suivantes : l'image, le PDF et ses empreintes, le contreseing et l'invalidation. Code ouvert dans l'éditeur en parallèle si le jury veut voir les fichiers.
25–31 min · focus code

1. Ne jamais faire confiance à l'image

  • Le pad envoie une data URL PNG — signatureImage.js vérifie le préfixe, décode le base64, contrôle les magic bytes PNG réels et plafonne à 200 Ko ;
  • un JPEG déguisé en PNG est refusé (testé) ;
  • le fichier validé est écrit sous storage/signatures/ — privé, nom régénéré.
Même philosophie que les uploads de candidature : on valide le contenu, jamais la déclaration. Fichier : src/services/ signatureImage.js (~60 lignes, lisible en séance).
25–31 min · focus code

2. Le PDF et ses empreintes

  • contractPdf.js génère le PDF (écriture asynchrone) avec une page de signatures : images, horodatages, empreintes ;
  • l'empreinte SHA-256 du PDF proposé est stockée — le candidat contresigne exactement ce document, c'est prouvable ;
  • le PDF final porte les deux signatures et sa propre empreinte.
Question probable : « valeur légale ? » — signature simple au sens eIDAS : intégrité + consentement + horodatage, pas une signature qualifiée. L'application l'affiche (modèles indicatifs).
25–31 min · focus code

3. Contre-signature et invalidation

  • Le candidat signe via son jeton de suivi — ouvrir ce lien neutralise la session école du navigateur (anti-usurpation) ;
  • consentement explicite obligatoire (case « j'ai lu et j'accepte ») ;
  • si l'école ré-édite le contrat : signature candidat et PDF signé invalidés et supprimés du disque — jamais d'état incohérent ;
  • un refus nettoie tous les fichiers du contrat (testé).
Le plus dur du lot : ne laisser aucun état incohérent. C'est là que le TDD a payé — les cas de nettoyage étaient des assertions avant d'être du code.
25–31 min · focus code

Sécurité en profondeur

  • CSRF : jeton de session, multipart vérifié après upload ;
  • CSP stricte : aucun script inline ;
  • bcrypt + limite 72 octets ;
  • uploads : magic bytes, stockage privé, accès scopé ;
  • rate limiting + réponses neutres (anti-énumération) ;
  • sessions régénérées, révocables, invalidées après reset ;
  • jetons email/reset hachés en base ;
  • purge RGPD automatique et journalisée.
Chaque mesure a sa fiche dans veille-securite.md : menace → source OWASP datée → décision → preuve testée.
